# Pith Self‑Evolution

Этот документ описывает, **как Pith учится на своём использовании**.  
Речь не про обучение моделей, а про эволюцию самого runtime: skills, prompts, policies, роутинг и сценарии.[file:1219][file:1238]

---

## 1. Зачем Pith нужна self‑evolution

Pith задуман как **self‑improving continuity runtime**:[file:1219]

- с каждым днём использования он должен лучше понимать реальные сценарии;
- уменьшать стоимость полезных ответов;
- снижать частоту типовых ошибок/фейлов;
- повышать предсказуемость поведения в продакшене.

Эволюция касается:

- **поведения** (какие шаги делает runtime в задачах),
- **правил** (policies, роутинг, thresholds),
- **процедур** (skills, промпты, шаблоны),  

но **не** весов базовых LLM‑моделей.[file:1271]

## 2. Архитектурный контур self‑evolution

Базовый пайплайн уже присутствует в коде Pith:[file:1219][file:1238]

```text
evaluator
  ↓
failure_miner
  ↓
patch_planner
  ↓
skill_compiler
  ↓
PatchGate
  ↓
rollout_manager
```

### 2.1. Evaluator

**Роль:** измерять качество работы runtime.

- Где: `core/evolution/evaluator.py`.  
- Что делает:
  - присваивает score шагам/таскам (например, `score.final`, `score.safety`, `score.coherence`);
  - добавляет reasons/tags (почему оценка такая);
  - пишет данные в метрики (`data/metrics/*.json`, логи).[file:1219]

Evaluator — источник правды для эволюции: без измерения нечему учиться.

### 2.2. Failure Miner

**Роль:** находить повторяющиеся сбои и слабые места.

- Где: `core/evolution/failure_miner.py`.  
- Что делает:
  - анализирует traces/tasks/metrics;
  - кластеризует фейлы по типам (ошибки, халюцинации, не туда выбранная модель, недоиспользование памяти и т.п.);
  - формирует candidate “failure patterns”.[file:1219][file:1238]

Результат: список “болевых точек”, по которым имеет смысл предлагать патчи.

### 2.3. Patch Planner

**Роль:** генерировать гипотезы патчей.

- Где: `core/evolution/patch_planner.py`.  
- Что делает:
  - на вход: failure patterns + контекст (конфиги, skills, policies);
  - на выход: предложения изменений:
    - новые/изменённые skills (процедуры);
    - корректировки prompts/policies;
    - изменения роутинга/thresholds.[file:1219]

PatchPlanner не применяет изменения сам — он генерирует **кандидатов**.

### 2.4. Skill Compiler

**Роль:** превращать предложения в формальные артефакты.

- Где: `core/evolution/skill_compiler.py`.  
- Что делает:
  - принимает патчи для skills/procedures;
  - компилирует их в структуры/файлы (например, `.md`/YAML в `skills/`), совместимые с runtime;
  - регистрирует новые skills в `SkillRegistry`.[file:1219]

Таким образом, гипотеза “нам нужен такой‑то паттерн действий” превращается в реальный skill, который runtime может использовать.

### 2.5. PatchGate (governance)

**Роль:** решать, что можно применять, а что нет.

- Где: `core/governance/patch_gate.py`.  
- Что делает:
  - сверяет предложенные патчи с правилами из `autonomy.yaml`;
  - автоматически одобряет безопасные изменения (см. ниже);
  - помечает рискованные патчи как требующие ручного review.[file:1219]

PatchGate — ключевой элемент управляемой автономии: он не даёт эволюции “разнести” ядро.

### 2.6. Rollout Manager

**Роль:** выкатывать и откатывать изменения.

- Где: `core/governance/rollout_manager.py`.  
- Что делает:
  - создаёт новые записи `runtime_versions`, `patch_candidates`, `patch_rollouts` (см. Roadmap Phase 3);[file:1219]  
  - применяет патчи в dev/staging/prod режимах;
  - отслеживает эффекты (метрики до/после);
  - умеет откатить изменения при деградации.

Таким образом, эволюция Pith — это не “подменили файл ночью”, а управляемый rollout с версионностью и rollback.

## 3. Границы и уровни автономии (`autonomy.yaml`)

Self‑evolution управляется конфигом `autonomy.yaml`.[file:1219]

### 3.1. Заблокированные зоны

В `autonomy.yaml` фиксируется список целей, которые **никогда** не могут быть изменены автоматически:

- ядро runtime (orchestrator, router, planner, memory manager, evaluator и т.п.);
- схемы данных (БД, episodes, artifacts);
- критичные интеграции (внешние API, биллинг и др.).

Это `blocked_targets`: любое предложение патча в эти зоны либо сразу отклоняется, либо допускается только через ручной review и отдельный процесс диплоя.

### 3.2. Безопасные зоны авто‑патчей

Есть список `safe_autopatch_targets` — то, что можно патчить автоматически (с логами и rollback):

- skills (новые/обновлённые процедуры);
- prompts / persona‑тексты / инструкции;
- policies и thresholds (в пределах заранее заданных диапазонов);
-, возможно, некоторые настройки роутинга, если риск низкий.[file:1219]

Идея: Pith может сам менять “поведение”, но не “организм”.

### 3.3. Уровни автономии (rings/tiers)

Для разных workspace’ов Pith может работать в разных режимах:

- **dev** — максимальная автономия: можно пробовать авто‑патчи шире, откатывать при необходимости.  
- **staging** — ограниченная автономия: auto‑patch только в безопасных зонах, с более жёсткими порогами.  
- **prod** — минимальная автономия: почти всё через review, auto‑patch только для заранее утверждённых категорий.[file:1219]

Это даёт возможность “крутить” эволюцию на себе и ранних пользователях, не рискуя продом.

## 4. Метрики эффекта эволюции

Чтобы self‑evolution не превратилась в веру, нужны метрики.[file:1219][file:1271]

Базовый набор:

- **Cost per useful response**  
  Сколько стоит “полезный” ответ (по оценке evaluator/пользователя) до и после патча.

- **Failure rate**  
  Частота сбоев по типам задач (например, incident‑фиксы, code‑changes, research).  
  Цель — снижать, но с учётом того, чтобы не ронять качество.

- **Time to resolution**  
  Сколько шагов/времени уходит на закрытие типовой задачи до/после.

- **Drift в выборе моделей / маршрутов**  
  Как меняется распределение использования моделей и agents после эволюции (не уходим ли в крайности).

Эти метрики должны отображаться в dashboard (`dashboard.py`) и привязываться к `runtime_versions` и `patch_rollouts`.[file:1219]

## 5. Связь с 6‑месячной Roadmap

Цели из `docs/ROADMAP_6M.md` (ретроспектива, динамический роутинг, мета‑память, проактивный аудит, интерфейс критика) — это **конкретные проявления self‑evolution**:[file:1219][file:1271]

- ретроспектива решений — потребитель данных evaluator/failure_miner;  
- динамическая коррекция роутинга — один из типов патчей (policies/weights);  
- мета‑память — дополнительный слой над памятью, который тоже может эволюционировать;  
- проактивный аудит — форма мета‑мониторинга;  
- интерфейс внешнего критика — источник сигналов для failure mining и patch planning.

Self‑evolution — это не отдельная фича, а **способ реализации этих способностей**.

---

## 6. Что принципиально не делает self‑evolution Pith

Важно явно зафиксировать ограничения:

- Не переписывает ядро runtime без участия человека.  
- Не обучает базовые LLM‑модели (не трогает их веса).[file:1271]  
- Не выходит за рамки `autonomy.yaml` даже в dev‑режиме.  
- Не меняет product‑доктрину — только поведение внутри её рамок.

Задача self‑evolution — сделать Pith **умнее как операционную систему**, а не “исчезнуть” в неконтролируемую автономию.
