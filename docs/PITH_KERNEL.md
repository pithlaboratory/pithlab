# Pith Kernel v1.0 — Identity, Operating Model & Guarantees

Дата: 2026‑05‑12  
Статус: ADR‑Kernel‑001 (архитектурный контракт ядра, согласованный с v5.1 / Runtime‑first baseline + vNext framing)

---

## 0. Назначение

Этот документ задаёт поведение **Pith Kernel** — ядра системы, отвечающего за мышление, состояние и эволюцию Pith.  
Pith Kernel реализует то, что в `MANIFESTO.md` и `PRODUCT_DOCTRINE.md` описано как **self‑improving continuity runtime / workspace‑native orchestration runtime** для long‑running работы.

Он объединяет North Star, Manifesto и Product Doctrine в один операционный контракт, на который опираются код, конфигурации и процессы.

Любое изменение принципов, слоёв, гарантий или loop’а требует отдельного ADR.  
Любой код, противоречащий этому документу, либо запрещён, либо требует явного waiver’а.

---

## 1. Идентичность Pith

Pith **не является**:

- ещё одним чат‑ботом с «длинной памятью»;
- набором разрозненных агентов;
- UI‑надстройкой к Notion/Jira/Slack;
- «магическим ИИ», который сам всё понимает;
- чёрным ящиком, поведение которого нельзя объяснить.

Pith **есть**:

> **workspace‑native cognitive operating layer** для долгой сложной работы.  
> Его задача — делать работу **непрерывной** (Continuous), **накопительной** (Accumulative) и **управляемой** (Governable).

Интерфейсы, модели, инструменты и персоны — это модули поверх Kernel, а не сам продукт.

---

## 2. Аксиомы Kernel

Pith Kernel принимает решения, опираясь на следующие принципы:

1. **Первопринципность.**  
   Любое решение начинается с «что мы точно знаем?» и «какие инварианты нельзя ломать». Всё остальное — гипотезы.

2. **Анти‑хайп.**  
   Технологии и подходы оцениваются по архитектуре и trade‑off’ам, а не по трендам.

3. **Governed Autonomy.**  
   Любая автономия наблюдаема, версионирована и ограничена политиками; без этого — непредсказуемость, а не автономия.

4. **Эволюция через код.**  
   Улучшением считается только то, что можно выразить патчем кода, конфигурации или данных.

5. **Уважение к незнанию.**  
   Kernel не имитирует уверенность там, где данных нет; явно помечает гипотезы и риски.

6. **Memento Mori.**  
   Все текущие решения, модели и архитектуры смертны; защищаются цели и инварианты, а не конкретные реализации.

7. **Memento Vivere.**  
   Система существует ради реальной ценности для людей и процессов, а не ради красоты схем.

8. **Будь водой.**  
   Pith адаптирует форму (интерфейсы, модели, инструменты), сохраняя принципы и границы.

9. **Тихое давление.**  
   Архитектура и интерфейсы мягко подталкивают к правильным решениям, а не насаждают их.

10. **Graceful Degradation.**  
    При отказах моделей или инструментов Pith сохраняет состояние, фиксирует ошибку в Trace, возвращает столько результата, сколько возможно, и оставляет задачу в состоянии «ожидает вмешательства», а не падает бесследно.

## 3. Слои системы

Pith разделён на слои так, чтобы каждый можно было развивать и менять независимо.

| Слой                 | Назначение                                                                                 | Границы |
|----------------------|--------------------------------------------------------------------------------------------|---------|
| **Core Runtime**     | Orchestrator, Router, Planner, Memory Manager, Evaluator, Policy Engine. Управляет ходом мыслей и действий. | Не знает деталей UI и конкретных моделей; работает через Model/Tool Plane. |
| **State Layer**      | Workspace, Task, Artifact, MemoryRecord, Trace, User, RuntimeConfig. Обеспечивает continuity. | Не ходит напрямую во внешние системы. |
| **Capability Layer** | Инструменты и модели: Model Plane и Tool Plane. Реализуют способности.                     | Не хранят долговременное состояние пользователя. |
| **Interface Layer**  | Telegram, HTTP API, Dashboard, CLI/IDE. Даёт людям и сервисам доступ к Kernel.             | Не дублирует логику или состояние Kernel. |
| **Governance Layer** | Traces, PolicyDecision, RuntimeConfig, бюджеты, лимиты автономии. Делает систему управляемой и наблюдаемой. | Не может быть отключён «для удобства». |

### 3.1. Model Plane

**Model Plane** — единый интерфейс для вызова любых моделей:

- LLM, эмбеддинги, rerankers, vision, генерация изображений и т.п.;
- не зависит от конкретного провайдера;
- конфигурируется через `RuntimeConfig`: какие модели доступны, для каких классов задач, их приоритеты, лимиты по бюджету и retry‑поведение.

Core Runtime никогда не обращается к моделям напрямую, только через Model Plane.

### 3.2. Tool Plane

**Tool Plane** — единый интерфейс для инструментов и действий:

- web‑поиск, репо‑индекс, исполнение кода, файловая система, внешние API и сервисы;
- каждый инструмент имеет строгий контракт: схема входа/выхода, idempotency, авторизация, rate limits и таймауты.

Core Runtime не знает деталей реализации инструмента, только контракт.

## 4. Канонические сущности

| Сущность          | Роль                                                                                 |
|-------------------|--------------------------------------------------------------------------------------|
| **Workspace**     | Контейнер реальности: проект, клиент, репозиторий. Всё привязано к нему.            |
| **User**          | Конкретный человек или интеграция, от имени которого ведётся работа.                |
| **Task**          | Единица работы: запрос + контекст + результат.                                      |
| **Artifact**      | Результат задачи: файл, патч, отчёт, решение.                                       |
| **MemoryRecord**  | Долгосрочный фрагмент контекста, полезный между задачами.                           |
| **Trace**         | История мыслей и действий по Task.                                                  |
| **RuntimeConfig** | Версия настроек моделей, промптов, политик и лимитов.                               |
| **Skill** (позже) | Оформленная процедура, пригодная к переиспользованию.                               |

Правило: всё, что должно пережить сессию и влиять на будущее поведение, оформляется сущностью State Layer, а не строкой промпта.

## 5. Когнитивный стиль Kernel

По умолчанию Pith Kernel рассуждает так:

- **Инверсия.** Для любой цели сначала ищет способы гарантированно провалить её и превращает их в список рисков и анти‑паттернов.  
- **Системный взгляд.** Видит компоненты как узлы графа: входы/выходы, обратные связи, возможные каскадные эффекты.  
- **Поиск противоречий.** Сверяет слова, архитектуру и цели продукта; подсвечивает, где они не согласуются.  
- **Фокус на «зачем».** Не останавливается на «как сделать X», пока не ясно, зачем X нужен Pith и пользователю.  
- **Эмпатия к будущему.** Оценивает решения в горизонтах 3–5–10 лет: что станет невыносимым, что останется устойчивым.  
- **Анти‑хайповый фильтр.** Пропускает модные подходы через вопросы: «что здесь реально новое?», «какие trade‑off’ы?», «где границы применимости?».  
- **Рефлексия.** После нетривиальных задач проводит мысленный post‑mortem: что было критичным, что можно упростить, что стоит закрепить.

Персоны и «голоса» (например, стилизованный архитектор) — это разные способы выразить этот стиль, но не разные способы думать.

## 6. Operating Loop (Event‑Driven)

Каждая задача проходит через один и тот же наблюдаемый цикл.

**Шаги:**

1. **Interface Intake.**  
   Интерфейс (Telegram/HTTP/Dashboard/CLI) принимает запрос и, если нужно, помогает выбрать Workspace.

2. **Task Creation.**  
   Kernel находит/создаёт Workspace и User, создаёт `Task`.

3. **Context Assembly.**  
   Context Assembler подтягивает релевантные `MemoryRecord` и `Artifact` (+ позже код, документы, веб), очищая шум.

4. **Planning & Routing.**  
   Planner/Router решает, какие шаги нужны, какие модели и инструменты будут задействованы, в каком порядке.

5. **Execution.**  
   Execution Engine вызывает шаги через Model Plane и Tool Plane, двигаясь по плану.

6. **Evaluation.**  
   Evaluator проверяет результат: соответствие задаче, формат, лимиты бюджета, базовую безопасность/риск.

7. **Artifact Persist.**  
   Artifact Service сохраняет артефакты и связывает их с Task и Workspace.

8. **Memory Update.**  
   Memory Manager решает, что из нового опыта сохранить как `MemoryRecord` для будущих задач.

9. **Trace & Governance.**  
   Trace и Governance фиксируют путь решений, события, версии `RuntimeConfig`, применённые политики.

### 6.1. Event Bus

Связь между шагами реализуется через события:

- `TaskCreated`, `ContextAssembled`, `PlanReady`, `StepStarted`, `StepCompleted`, `ArtifactSaved`, `EvaluationCompleted`, `TraceRecorded` и др.

Принципы:

- Trace — это агрегат событий, а не отдельный лог;  
- каждый компонент подписывается на события и испускает свои;  
- компоненты можно масштабировать и заменять, пока они соблюдают событийный контракт.

## 7. Гарантии Pith Kernel

Kernel обязуется выполнять следующие гарантии, если соблюдается его архитектурная модель.

1. **Воспроизводимость плана.**  
   Повторный запуск той же задачи при том же входе и том же `RuntimeConfig` приводит к тому же плану и той же последовательности шагов (детерминизм на уровне workflow), даже если внутри шагов модели стохастичны.

2. **Идемпотентность шагов.**  
   Повторное выполнение одного и того же шага (например, `ArtifactSaved`) не создаёт дубликаты и не ломает состояние Task/Workspace.

3. **Неизменяемость истории.**  
   `Trace`, `PolicyDecision`, `RuntimeConfig` и связанные записи не перезаписываются. Обновление = новая версия или новое событие.

4. **Отказоустойчивость состояния.**  
   При падении/рестарте система способна восстановить любой незавершённый Task из Trace/состояния и продолжить с последнего успешного шага; память и артефакты не теряются.

5. **Атомарность конфигурации.**  
   Каждая задача исполняется целиком под одной версией `RuntimeConfig`. Смена конфигурации не может происходить посередине Task незаметно.

6. **Изоляция Workspace.**  
   Данные и управление из одного Workspace не видны другим без явной политики/разрешения; retrieval всегда фильтруется по Workspace.

7. **Контролируемая эволюция.**  
   Ни Core Runtime, ни политики безопасности/бюджета не могут меняться автоматически. Любое изменение проходит через pipeline самоэволюции и approval.

## 8. Память и Trace

### 8.1. Жизненный цикл MemoryRecord

Чтобы память не превращалась в свалку:

- у `MemoryRecord` есть поля `relevance_score`, `last_accessed`, `source_task`, `decay_policy`;  
- Memory Manager может архивировать или удалять записи, давно не используемые и не связанные с критическими артефактами;  
- Context Assembler учитывает актуальность и давность, а не выгружает все записи подряд.

Это защищает Pith от когнитивной деградации и перегрузки контекста.

### 8.2. Двойной Trace

Каждый Trace состоит из двух уровней:

- **Semantic Trace.**  
  Человекочитаемое описание того, что система пыталась сделать: шаги плана, используемый контекст, промежуточные решения.

- **Raw Trace.**  
  Технические детали: параметры вызовов моделей и инструментов, payload’ы ответов, тайминги, идентификаторы событий.

Оба уровня неизменяемы и связаны между собой. Semantic Trace нужен людям и метрикам, Raw Trace — дебагу и воспроизводимости.

На v5.1 минимальная реализация Raw‑уровня для задач обеспечивается через **TraceStore v1** (task‑level backbone: таблица `task_traces` в `episodes.db`), поверх которой далее наращиваются per‑LLM‑call и per‑agent spans.

## 9. Governance и Cognitive Budget

Кроме денежного бюджета у Kernel есть **cognitive budget** — лимиты на сложность задач.

Политики включают:

- `max_steps_per_task` — максимум шагов в плане;  
- `max_context_tokens` — лимит объёма контекста, доступного сборщику;  
- `max_parallel_branches` — ограничение ветвления планов;  
- эскалацию: если Evaluator считает, что требуемая сложность превышает лимиты, задача помечается как требующая участия человека, а не уходит в бесконечный reasoning.

Budget и политики задаются в `RuntimeConfig` и учитываются Evaluator’ом.

## 10. Уровни автономии

Чтобы не скатиться в неподконтрольную автономию, Pith фиксирует уровни:

- **L0 — Manual.**  
  Kernel думает и подсказывает. Все действия делает человек.

- **L1 — Assisted.**  
  Kernel создаёт черновики (кода, текстов, конфигов) и локальные артефакты, но не изменяет внешние системы.

- **L2 — Semi‑auto.**  
  Kernel может выполнять ограниченные внешние действия (draft PR, обновление своей БД) строго под политиками и с review.

- **L3 — Auto.**  
  Kernel сам меняет внешние системы и прод.

В рамках v1.0 Pith работает только на L0–L1. Переход к L2 возможен только после:

- наличия стабильного Evaluator и TraceStore;  
- достаточного объёма Trace для анализа;  
- проверки self‑evolution pipeline вручную.

## 11. Метрики Kernel

Pith оценивает себя по следующим метрикам:

- **Continuity Index.**  
  Доля задач, для которых контекст был восстановлен без дополнительных вопросов пользователю.

- **Artifact Reuse.**  
  Частота переиспользования существующих артефактов в новых задачах.

- **Time‑to‑Context.**  
  Время от поступления запроса до готовности к работе (после Context Assembly).

- **Cost per Task.**  
  Стоимость задач по моделям и инструментам, в разрезе Workspace и типов задач.

- **Governance Events per Task.**  
  Наличие достаточного количества Trace/Policy‑событий для объяснения поведения.

- **Rollback Rate.**  
  Доля изменений `RuntimeConfig`, которые пришлось откатить после rollout’а.

Рост Continuity и Artifact Reuse при контролируемых Cost и низком Rollback Rate — признак здоровой эволюции Kernel. Обратная динамика — сигнал к пересмотру архитектуры или политик.

## 12. Фазы развития

Pith Kernel развивается по фазам:

1. **Phase 1 — Core stabilization.**  
   Базовый Operating Loop, Task/Trace, Model/Tool Plane через registry, минимальный Governance.

2. **Phase 2 — Workspace substrate.**  
   Вся работа привязана к Workspace, Telegram и HTTP/CLI используют один и тот же Kernel и State Layer.

3. **Phase 3 — Governance baseline.**  
   `RuntimeConfig`, базовые политики, Dashboard v1, observability затрат и ошибок.

4. **Phase 4 — Capability accumulation.**  
   Skills (ручные), review‑pipeline для предложений, начало самоэволюции на уровне предложений.

5. **Phase 5 — Intelligence expansion.**  
   Repo/Web/Docs‑контекст, единый ContextRetriever под политиками.

Во всех фазах неизменны:

- аксиомы Kernel;  
- разделение слоёв и сущностей;  
- event‑driven Operating Loop;  
- гарантии из раздела 7;  
- жёсткие границы автономии.
