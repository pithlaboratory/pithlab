# PITH System Vision

> PITH — это операционный AI-слой поверх работы и компании.  
> Он связывает диалог, память, задачи, внешние системы и наблюдаемость в одну живую систему.

---

## 1. Mission & Identity

PITH — это операционная система поверх LLM, которая помогает людям и командам **двигать реальные задачи**, а не просто “чатиться с моделью”.

- PITH — это не один бот, а **runtime + оболочка**.
- PITH — это “разумный интерфейс” к архитектуре, коду, процессам и знаниям.
- PITH — это платформа, которая со временем **эволюционирует вместе с пользователем и компанией**.

Главная цель: минимизировать трение между “идея/задача” и “конкретный выполненный шаг”, сохраняя при этом прозрачность, контроль и наблюдаемость.

---

## 2. User-Facing Surfaces

PITH — многоинтерфейсная система. У неё несколько точек входа, но одно ядро.

**Основные поверхности:**

1. **Telegram / Chat**
   - Быстрый вход, поручения, вопросы, короткие циклы.
   - Notifications, статус задач, быстрые правки.
   - Governance-guards, UX-ответы, loading UX.

2. **Web Workspace**
   - Канбан/лента задач, timeline эпизодов, артефакты.
   - Просмотр памяти, истории решений, метаданных.
   - Управление задачами, ручные правки, review.

3. **Voice Interface**
   - Голосовой диалог (input/output) поверх того же runtime.
   - Сценарии “в дороге / в движении / hands-free”.
   - Та же память и те же задачи, другие modalities.

4. **API / SDK**
   - REST API & SDK для интеграций (запуск агентных задач, polling статусов, работа с агентами).
   - “PITH как сервис” для других систем и автоматики.

5. **Product Shell / Landing**
   - Публичный визуальный слой: лендинг, демо, API explorer.
   - Позиционирование PITH как продукта, а не только внутреннего инструмента.

Каждая новая поверхность **подключается к тому же runtime**: общая память, общие агенты, общая observability.

## 3. Core Capabilities

PITH — не просто чат. У него есть набор базовых способностей, которые должны быть всегда:

1. **Диалог и адаптация**
   - Понимать контекст диалога, режим (архитектура, diagnostics, обычная помощь).
   - Подстраиваться под стиль, глубину и формат задач пользователя.
   - Поддерживать длинные отношения (sessions, workspaces, history).

2. **Память**
   - Краткосрочная: текущий диалог, активные задачи.
   - Долгосрочная: эпизоды, решения, документы, предпочтения.
   - Workspace-aware: память разделяется по рабочим пространствам/командам.

3. **Интернет и внешние источники**
   - Поиск и чтение веб-страниц.
   - Извлечение фактов и структурированных знаний.
   - Проверка гипотез, сравнение альтернатив, обновление контекста.

4. **Код и репозитории**
   - Чтение репозиториев (локальных и удалённых).
   - Понимание архитектуры, модулей, схем, API.
   - Связка “код ↔ задачи ↔ observability”.

5. **Skills / Tools / Agents**
   - Registry инструментов (web search, code tools, DB, внешние API).
   - Подключение новых skills, полезных для системы и workspace.
   - Агентные роли (researcher, analyst, executor, etc.).

6. **Task & Workflow Execution**
   - Создание, планирование и выполнение задач.
   - Многошаговые workflows, decomposition, orchestration.
   - Чёткий lifecycle: created → planned → executing → completed/failed.

7. **Observability**
   - Traces (task_id, trace_id, workspace_id, episode_id).
   - Metrics (latency, cost, success/fail, tokens).
   - Logs & events (task_started, tool_called, task_failed, etc.).
   - Eval & feedback loops.

## 4. Company / Workspace Layer

PITH — система не только для одного человека, но и для команд и компаний.

**Основные сущности:**

- **Workspace**  
  - Единица изоляции памяти и задач.
  - Привязан к пользователю / команде / проекту.

- **Roles & Agents**
  - Личные агенты (личный ассистент).
  - Командные агенты (team ops, monitoring).
  - Организационные агенты (governance, compliance).

- **Policies & Governance**
  - Ограничения по данным (workspace isolation, leak/danger guards).
  - Политики использования LLM и инструментов.
  - Классы автономии (L0–L2: только советы → ассист с подтверждением → ограниченная автономия).

---

## 5. Evolution & Self-Improvement

PITH должен уметь **постепенно улучшать себя** в границах, заданных людьми.

Вектор эволюции:

1. **Skill Acquisition**
   - Выявление недостающих способностей (по диалогам, задачам).
   - Поиск/подключение новых skills (инструменты, агенты, интеграции).
   - Управление “skill graph” для каждого workspace.

2. **Repo & Knowledge Ingestion**
   - Чтение и освоение новых репозиториев (код, документация).
   - Обновление внутренних моделей контекста (архитектура, домен).
   - Привязка знаний к конкретным workspaces и агентам.

3. **Eval & Feedback**
   - Автоматические eval-скрипты по ключевым сценариям.
   - User feedback (up/down) и ручной review.
   - Изменение маршрутов, конфигураций и default-паттернов на основе данных.

4. **Adaptive Strategies**
   - Настройка режимов (экономия токенов, глубина анализа).
   - Адаптация к стилю пользователя / команды.
   - Переключение моделей / агентов для разных задач.

Эволюция PITH — это **не магическая самоперепись кода**, а системное улучшение:
- конфигов, маршрутов, skills,
- eval-политик и observability,
- UX поверх runtime.

## 6. Observability as a First-Class Feature

PITH — trace-ready и eval-ready по дизайну.

**Принципы:**

- Любая задача имеет trace: `task_id`, `trace_id`, `workspace_id`, `episode_id`.
- Каждое действие (создать задачу, вызвать tool, записать память, выдать ответ) оставляет событие.
- Стоимость, latency, модели, eval — всё логируется и доступно через UI/API.

**Обязательные элементы:**

- Episodes DB (диалоги, ответы, метаданные).
- Trace/metrics pipeline (task_started, task_completed, task_failed, tool_called, etc.).
- Dashboards:
  - по задачам;
  - по пользователям/workspaces;
  - по стоимости и LLM usage;
  - по качеству (eval/feedback).

Observability — это не “дополнение для инженеров”, а **часть интерфейса PITH как продукта**.

## 7. Product Shape & UX

PITH должен выглядеть и ощущаться как современный продукт, а не как набор внутренних скриптов.

**Визуальный слой:**

- Лендинг / маркетинг-страница с:
  - историей продукта,
  - демо и live API explorer,
  - roadmap,
  - clear positioning.

- Продуктовый UI:
  - workspace dashboard,
  - agent studio,
  - task & episode timelines,
  - artifact browser,
  - observability dashboards.

**UX-принципы:**

- Один главный action на экран (без перегруза).
- Чёткие состояния (loading, empty, error, success).
- Голос и текст — равноправные каналы.
- Human-in-the-loop: лёгкий review/approve, feedback, rollback.

---

## 8. Autonomy & Boundaries

PITH не должен “самопроизвольно захватывать мир”. Мы чётко фиксируем границы:

- PITH действует **в интересах пользователя/команды** и в рамках заданных политик.
- PITH **не**:
  - выполняет разрушительные действия без подтверждения;
  - раскрывает системные промпты и секреты;
  - нарушает workspace isolation.
- PITH **может**:
  - предлагать изменения/действия;
  - исполнять явно одобренные workflows;
  - развивать свои skills и конфиги в рамках governance.

## 9. Relation to Runtime & Master Plan

Этот документ описывает **внешний вид и поведение системы PITH** как продукта и операционного слоя.

- Runtime (`core`, `memory`, `task_service`, `planner`, `toolplane`, `observability`) обеспечивает технический фундамент.
- `PITH_MASTER_PLAN` описывает **этапы и задачи**, через которые мы придём к этому видению.
- Любые архитектурные/продуктовые решения должны проверяться на согласованность с этим vision:
  - добавляем ли мы новую поверхность?
  - усиливаем ли мы core capabilities?
  - помогаем ли evolvability и observability?
  - остаёмся ли в заданных границах автономии?
