# Postmortem: голос и повторяющиеся паттерны (2026‑04)

**Status:** HISTORICAL · LESSONS APPLIED  
**Scope:** Поведение голоса Pith, смешение personae и повторяющиеся шаблоны в ответах.

---

## 1. Контекст

Диалог от 28.04.2026 (Telegram):

- Пользователь задаёт серию вопросов про путь к AGI, самоэволюцию и честный план развития Pith.
- В ответ несколько раз подряд возвращается один и тот же шаблон:
  - блоки `[TERA] / [PLEX] / [HEX] / [CODA]` с одинаковой структурой;
  - отсутствие реального содержимого под запросом;
  - повторение формата, хотя пользователь прямо указывает “опять такой же ответ”.

Параллельно в истории были ответы в роли **Viktor Vaughn** (persona), хотя по доктрине Pith — операционный runtime, а не персонаж.

---

## 2. Что пошло не так

### 2.1. Смешение голосов

- Pith отвечал то от лица системы (“Pith: …”), то от лица персонажа Viktor.
- Это нарушило контракт идентичности: **Pith — runtime, а не персона** (см. `IDENTITY.md`, `PITH_MASTER_PLAN.md` §10/§22/§24).

### 2.2. Повторяющиеся шаблоны без адаптации

- На стратегический запрос (“как нам приблизиться к AGI / путь к самоэволюции”) несколько раз пришёл один и тот же каркас:
  - `[TERA] Ничего не найдено по запросу.`
  - `[PLEX] ✓ Response structure: OK …`
  - `[HEX] 🔮 Trend …`
  - `[CODA] ✓ No code changes required …`
- Структура не менялась, несмотря на явный сигнал пользователя, что формат его не устраивает.

### 2.3. Отсутствие уточняющих вопросов

- Запросы были широкими (“расскажи свои мысли…”, “реальный план к AGI”).
- Pith не прояснил:
  - уровень (архитектура / поведение / продукт),
  - горизонт (текущий runtime vs 3–5 лет),
  - формат (эссе, roadmap, конкретные шаги).

---

## 3. Причины на уровне оркестратора

### 3.1. Нет явного разделения “боевой голос” vs persona

- В конфиге/коде не было жёсткого флага “runtime‑voice only”.
- Persona могла “подмешиваться”, если ранее фигурировала в истории.
- Оркестратор не различал экспериментальные persona‑сессии и боевой режим.

### 3.2. Нет детектора повторяющихся структур

- Не сравнивались структура/шаблон ответа с последними N ответами.
- Не было правила: “если пользователь явно недоволен и мы даём схожую структуру, нужно менять стратегию, а не повторять шаблон”.

### 3.3. Нет протокола для мета‑/AGI‑запросов

- Для запросов уровня “путь к AGI / самоэволюция / честный план” не было обязательного шага уточнения.
- Pith “угадывал” формат вместо того, чтобы уточнить ожидания.

---

## 4. Что решено изменить (LESSONS → APPLIED)

### 4.1. Голос Pith по умолчанию

- В боевом режиме Pith **говорит только от имени runtime**:
  - без ролевых масок и персонажей;
  - язык: “Pith как runtime делает X / не делает Y”.
- Любые persona‑режимы (Viktor и т.п.) возможны только:
  - через явный флаг/конфиг;
  - в отдельном лабораторном/игровом контексте, не влияющем на основной runtime.

**Зафиксировано в:** `docs/IDENTITY.md`, `docs/PITH_MASTER_PLAN.md` (§1, §10, §22, §24).

### 4.2. Детектор повторяющихся паттернов

- Для high‑level запросов оркестратор должен:
  - сравнивать структуру планируемого ответа с последними N (2–3) ответами;
  - учитывать явные сигналы неудовлетворённости пользователя.
- Если структура совпадает “под копирку” и пользователь недоволен → форсировать смену стратегии:
  - задать уточняющий вопрос,
  - либо выдать короткий честный ответ без тяжёлого шаблонного каркаса.

**Интеграция:** требования внесены в runtime‑контекст/дев‑гайд (PITH_RUNTIME_CONTEXT_PROTOCOL_V1 / PITH_DEV_CONTEXT).

### 4.3. Обязательный уточняющий вопрос для мета‑запросов

Для запросов вида:

- “как нам приблизиться к AGI”,
- “расскажи свои мысли о будущем Pith…”
- “что ты реально хочешь, чтобы мы сделали…“

введено правило:

1. Сначала **ровно один уточняющий вопрос** по ключевому измерению (уровень: архитектура / поведение / продукт / бизнес).
2. Затем — развёрнутый ответ на согласованном уровне.

**Интеграция:** отражено в инструкциях для ассистентов и дев‑контексте как часть self‑improvement/evolution.
