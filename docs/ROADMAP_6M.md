Pith Roadmap — горизонты 6 месяцев
Status: WORKING / V1
File role: 6‑month capability roadmap for the self‑improving continuity runtime
Scope: надстройка над базовым runtime/workspace‑слоем (фазы 1–3), фокус на self‑evolution и continuity, не на “новых агентах” или AGI.

Этот документ описывает не все фичи Pith, а именно те способности, которые должны появиться в течение ближайших ~6 месяцев поверх базового runtime и workspace‑слоя.
Фокус: self‑improving continuity runtime, а не “новые агенты” или AGI‑обещания.

0. База, на которую опираемся
Эти цели предполагают, что к этому моменту уже выполнены фазы 1–3 из IMPLEMENTATIONROADMAPV1:

Стабильный runtime (Router, RuntimePlanner, Orchestrator, MemoryManager, Evaluator).

WorkspaceService / TaskService / ArtifactStore + базовый HTTP/API.

Governance baseline: evaluation schema, версии runtime, rollback, базовый dashboard.

Дальше — надстройка: что Pith должен уметь к горизонту 6 месяцев.

1. Автоматическая ретроспектива решений
1.1. Что это такое
Pith регулярно (по расписанию или по запросу) анализирует цепочки принятых решений (task traces, episodes) и строит семантическую ретроспективу:

какие шаги привели к успеху / провалу;

где мы переусиливали один “голос” (исследование vs исполнение, быстрые модели vs тяжёлые);

какие альтернативы рассматривались и были отброшены.

Результат — не просто лог, а объяснение “почему тогда выбрали X, хотя Y был возможен”.

1.2. Зачем пользователю
Видеть не только “что сделал Pith”, но и “как он думал по пути”.

Ловить архитектурные и продуктовые перекосы по логам, а не по боли (например, “мы всегда переоцениваем быстрые фиксы”).

Это критично для команд, которые хотят доверять runtime в продакшене.

1.3. Модули и артефакты
core.evolution.evaluator — выдаёт оценку качества по шагам/таскам.

data/episodes.db — источник эпизодической истории.

data/metrics/router_stats.json и другие метрики — сырьё для анализа.

Новый сервис RetrospectiveService (планируется):

агрегирует task traces;

строит summary по workspace/типам задач;

отдаёт это в dashboard/API.

2. Динамическая коррекция роутинга
2.1. Что это такое
Сейчас роутинг в Pith во многом статичен (lanes, веса, правила). Цель на 6 месяцев — сделать его адаптивным:

корректировать веса моделей/lanes на основе накопленной статистики (качество/стоимость/фейлы);

учитывать тип задач, workspace и даже конкретный сценарий;

уметь явно переключать стратегии (например, “максимальная экономия” vs “максимальное качество”).

2.2. Зачем пользователю
Меньше ручного тюнинга “под каждую команду/проект/репу”.

Снижение cost_per_useful_response без потери качества ответа.

Возможность объяснить: “почему сейчас выбрана именно эта модель/маршрут”.

2.3. Модули и артефакты
core.runtime_planner, core.cognition_router — применяют новые веса/стратегии.

core.modelregistry — хранит конфигурацию моделей и lanes.

core.evolution.failure_miner — выделяет паттерны ошибок, связанные с роутингом.

data/metrics/router_stats.json — источник для обучения/адаптации.

3. Мета‑память с приоритетами забывания
3.1. Что это такое
Сейчас память в основном эпизодическая (episodes + vector search). Цель — добавить слой meta‑memory:

помечать эпизоды по важности (например, решения, изменившие код/архитектуру/процессы);

автоматом архивировать низкоприоритетный шум (одноразовые уточнения, проходные диалоги);

уметь “сжимать” историю, сохраняя причинные связи (почему X привело к Y).

3.2. Зачем пользователю
Меньше когнитивного мусора в ответах (“я припомню всё подряд”).

Быстрая навигация к реально важным решениям по проекту.

Ускорение работы — меньше контекста гоняется туда‑сюда без пользы.

3.3. Модули и артефакты
core.memory.manager, core.memory.context — текущие примитивы памяти.

data/episodes.db — база эпизодов.

Новый слой MetaMemoryIndex (планируется):

хранит “веса значимости” эпизодов;

управляет архивированием/обрезкой;

обеспечивает API вроде get_key_decisions(workspace, timeframe).

4. Проактивный аудит качества
4.1. Что это такое
Сейчас оценка качества работает в основном как сервис “после факта”. Цель на 6 месяцев — сделать проактивный аудит.

Механика:

Для “крупных” или high‑impact ответов (например, длинные стратегии, инцидент‑фиксы, важные патчи) запускается лёгкий self‑check.

Этот слой проверяет:

не ушёл ли ответ в шаблон;

не пропущен ли важный контекст из памяти/workspace;

нет ли скрытых допущений без явной оговорки.

4.2. Зачем пользователю
Меньше “воды” и повторяющихся общих советов.

Больше явных предупреждений “я не уверен” и предложений, как проверить вывод.

Повышение доверия к runtime: он сам следит за своим качеством, а не только за ценой.

4.3. Модули и артефакты
core.evolution.evaluator — повторная оценка ответов.

Новый QualityMonitor (планируется):

конфигурирует триггеры (по длине, типу задачи, workspace);

сохраняет результаты аудита.

Интеграция с dashboard.py для визуализации качества во времени.

5. Интерфейс внешнего критика
5.1. Что это такое
Сейчас пользователь может сказать “не то” или “плохо”, но это не структурировано. Цель — добавить интерфейс внешнего критика, который:

позволяет явно сказать: “здесь ты предвзят”, “здесь ты пропустил X”, “здесь ты выбрал слишком дешёвую/дорогую модель”;

превращает такие сигналы в данные для failure mining и коррекции поведения;

показывает в ретроспективах: “вот где нас критиковали, вот что мы поменяли”.

5.2. Зачем пользователю
Воздействовать на Pith не только через промпт, но и через правила.

Транслировать свой опыт/смещения в систему, чтобы она адаптировалась под конкретную команду/продукт.

Видеть, что feedback не исчезает, а конкретно меняет runtime.

5.3. Модули и артефакты
Новый CriticInterface:

API/UX для фиксации критики (тип, причина, тяжесть);

привязка к конкретным трассам/ответам.

core.evolution.failure_miner — кластеризует такие сигналы и ищет паттерны.

core.evolution.patch_planner + policies — используют сигналы для изменения поведения.

6. Как это связано с текущим Implementation Roadmap
IMPLEMENTATIONROADMAPV1.md задаёт скелет: фазы 1–5 (core stabilization → workspace substrate → governance → capability accumulation → intelligence expansion).

Этот ROADMAP_6M.md отвечает на вопрос:

Что конкретно Pith должен уметь “над” этим скелетом, чтобы называться self‑improving continuity runtime, а не просто orchestration‑фреймворком.

Каждая цель здесь:

усиливает хотя бы один критерий: continuity / memory / orchestration / long‑running work / observability & governance;

опирается на уже спроектированные модули (evaluator, failure miner, PatchGate, autonomy.yaml и т.п.);

двигает Pith в сторону governed self‑evolution, а не “магического AGI”.
